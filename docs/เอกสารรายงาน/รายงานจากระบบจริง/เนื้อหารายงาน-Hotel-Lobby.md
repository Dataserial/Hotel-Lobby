# ระบบจัดการโรงแรม Hotel-Lobby

ฉบับร่างเนื้อหาจากโค้ดและเอกสารในโครงการ ตรวจข้อมูลเมื่อ 10 ตุลาคม 2569

เอกสารนี้เสนอเนื้อหา 5 บทสำหรับจัดทำรายงานตามรูปแบบมหาวิทยาลัยขอนแก่น ชื่อผู้จัดทำ รหัสนักศึกษา อาจารย์ รายวิชา และข้อมูลการศึกษาอยู่ระหว่างรอข้อมูลจากผู้จัดทำ ผลการทดสอบที่กล่าวถึงเป็นผลตามบันทึกในโครงการ ไม่ใช่ผลการรันทดสอบใหม่ระหว่างเขียนรายงาน

## คำนำ

รายงานฉบับนี้จัดทำขึ้นเพื่ออธิบายการพัฒนาเว็บแอปพลิเคชันระบบจัดการโรงแรม Hotel-Lobby ครอบคลุมความเป็นมา วัตถุประสงค์ แนวคิดที่เกี่ยวข้อง การออกแบบฐานข้อมูล การดำเนินงาน ผลการพัฒนา และข้อจำกัดของระบบ โดยศึกษาจากซอร์สโค้ด เอกสารข้อกำหนด API และบันทึกการตรวจรับที่อยู่ในโครงการ

ระบบประกอบด้วยเว็บไซต์สาธารณะสำหรับค้นหาห้องว่าง และเว็บไซต์สำหรับผู้ดูแลระบบกับพนักงานต้อนรับในการจัดการผู้เข้าพัก ห้องพัก การจอง การบันทึกรับและคืนเงิน ตลอดจนการเช็กอินและเช็กเอาต์ รายงานให้ความสำคัญกับความถูกต้องของการจองและความสอดคล้องระหว่างรายการเงินกับสถานะการเข้าพัก ข้อมูลผลการทดสอบระบุขอบเขตและแหล่งหลักฐานเพื่อให้ผู้อ่านแยกผลที่ตรวจในสภาพแวดล้อมทดลองออกจากงานที่ยังต้องตรวจสอบก่อนนำไปใช้จริงได้

## บทที่ 1 บทนำ

### 1.1 ความเป็นมาและความสำคัญ

งานต้อนรับของโรงแรมต้องประสานข้อมูลหลายส่วน ได้แก่ ห้องพัก ผู้เข้าพัก ช่วงวันจอง สถานะการเข้าพัก และรายการชำระเงิน หากข้อมูลเหล่านี้แยกจากกัน พนักงานต้องตรวจสอบหลายแหล่งก่อนยืนยันรายการ และอาจเกิดความไม่สอดคล้องระหว่างห้องที่แสดงว่าว่างกับห้องที่ได้รับการจองแล้ว โครงการนี้จึงกำหนดให้ข้อมูลการจองและการดำเนินงานเชื่อมโยงกันผ่านบริการกลาง

ประเด็นสำคัญของระบบคือการป้องกันการจองห้องเดียวกันในคืนเดียวกันเมื่อมีคำขอพร้อมกัน และการป้องกันยอดเงินที่ไม่สัมพันธ์กับหลักฐานรับหรือคืนเงิน โค้ดใช้ข้อมูลสิทธิ์ครอบครองห้องรายคืนและธุรกรรมฐานข้อมูลเพื่อควบคุมการจอง พร้อมเก็บรายการเงินที่เชื่อมโยงกับการจองเพื่อให้ตรวจสอบย้อนหลังได้ ส่วนเว็บไซต์สาธารณะแสดงเฉพาะข้อมูลห้องว่างตามขอบเขตที่กำหนด [1], [2], [3]

ไม่มีหลักฐานการสำรวจโรงแรมหรือข้อมูลสัมภาษณ์ผู้ใช้งานจริงในชุดเอกสารที่ใช้เขียนรายงาน จึงอธิบายปัญหาเป็นบริบทการออกแบบระบบ ไม่สรุปว่าปัญหาดังกล่าวเกิดขึ้นจริงในโรงแรมกรณีศึกษาแห่งใด

### 1.2 วัตถุประสงค์

1) พัฒนาเว็บแอปพลิเคชันสำหรับจัดการข้อมูลห้องพัก ประเภทห้อง ผู้เข้าพัก และการจองในระบบเดียวกัน

2) กำหนดสิทธิ์ผู้ดูแลระบบและพนักงานต้อนรับให้สอดคล้องกับการทำงานผ่าน API

3) ควบคุมความถูกต้องของการจอง รับเงิน คืนเงิน เช็กอิน และเช็กเอาต์ด้วยกฎสถานะและธุรกรรมฐานข้อมูล

4) ให้บุคคลทั่วไปค้นหาห้องว่างจากบริการเดียวกับที่พนักงานใช้ โดยเปิดเผยเฉพาะข้อมูลห้องที่จำเป็น

5) จัดทำเอกสารและหลักฐานการทดสอบเพื่อสนับสนุนการตรวจสอบและการพัฒนาระบบต่อไป

### 1.3 ขอบเขตของระบบ

ผู้ดูแลระบบจัดการบัญชีผู้ใช้ ห้องพัก และประเภทห้อง รวมทั้งเข้าถึงรายงานยอดรับและคืนเงินสะสมได้ พนักงานต้อนรับใช้งานข้อมูลผู้เข้าพัก ค้นหาห้องว่าง สร้างและดำเนินการเกี่ยวกับการจอง บันทึกรายการเงิน และเช็กอินหรือเช็กเอาต์ได้ การแก้ไขข้อมูลห้องและประเภทห้องจำกัดไว้สำหรับผู้ดูแลระบบตามเส้นทาง API ปัจจุบัน [4]

เว็บไซต์สาธารณะค้นหาห้องว่างตามวันเข้าพัก วันออก และจำนวนผู้เข้าพัก พร้อมแสดงรายละเอียดเพื่อติดต่อเคาน์เตอร์ เว็บไซต์ส่วนนี้ยังไม่สร้างการจองแบบไม่เข้าสู่ระบบและไม่รับชำระเงินออนไลน์ การบันทึกการรับหรือคืนเงินเป็นการบันทึกการเคลื่อนย้ายเงินจริงที่พนักงานดำเนินการภายนอกระบบ ไม่มีการเชื่อม Payment Gateway และไม่จัดเก็บรายละเอียดบัตร [2], [5]

รายงานผู้ดูแลระบบแสดงยอดจากบัญชีรายการเงินตลอดช่วงข้อมูลทั้งหมด ยังไม่มีตัวกรองช่วงวันที่หรือกราฟยอดรายวัน การประเมินในรายงานใช้โค้ดและบันทึกการทดสอบในเครื่อง ไม่มีข้อมูลการประเมินความพึงพอใจ ประสิทธิภาพภายใต้ภาระจริง หรือหลักฐานเปิดใช้งานในโรงแรมจริง [3], [6]

### 1.4 ประโยชน์ที่คาดว่าจะได้รับ

ระบบช่วยให้พนักงานเรียกใช้ข้อมูลห้อง ผู้เข้าพัก การจอง และรายการเงินผ่านกระบวนการเดียวกัน มีเงื่อนไขตรวจสอบก่อนเปลี่ยนสถานะ และมีรายการอ้างอิงสำหรับตรวจสอบธุรกรรม ข้อมูลห้องว่างสำหรับบุคคลทั่วไปกับพนักงานมาจากบริการร่วมกัน จึงลดความแตกต่างจากการเขียนกฎค้นหาแยกหลายชุด

ประโยชน์ด้านการลดเวลา ลดความผิดพลาด หรือเพิ่มความพึงพอใจยังเป็นผลที่คาดหวัง ต้องมีการวัดก่อนและหลังหรือการทดลองกับผู้ใช้งานจริงก่อนกล่าวอ้างเป็นผลสำเร็จเชิงปริมาณ

## บทที่ 2 แนวคิดและเทคโนโลยีที่เกี่ยวข้อง

### 2.1 เว็บแอปพลิเคชันและสถาปัตยกรรมระบบ

โครงการแยกส่วนแสดงผลไว้ในโฟลเดอร์ client และส่วนให้บริการข้อมูลไว้ในโฟลเดอร์ server ฝั่งผู้ใช้ส่งคำขอ HTTP ไปยัง API ซึ่งตรวจข้อมูลและสิทธิ์ก่อนเรียกบริการและฐานข้อมูล การแยกส่วนทำให้หน้าจอสามารถใช้กฎธุรกิจเดียวกันผ่าน API และทำให้การทดสอบบริการไม่จำเป็นต้องอาศัยการกดหน้าจอทุกกรณี [1], [4], [5]

เส้นทางการทำงานหลักคือผู้ใช้ → React/TypeScript → Express API → บริการการจองหรือรายการเงิน → Prisma → MongoDB รูปแบบนี้เป็นคำอธิบายจากโครงสร้างโค้ดปัจจุบัน ไม่ใช่หลักฐานว่าระบบถูกติดตั้งตามสถาปัตยกรรมนี้บนบริการโฮสต์จริงแล้ว

### 2.2 เทคโนโลยีส่วนแสดงผล

ส่วนแสดงผลใช้ React และ TypeScript โดยมี Vite สำหรับพัฒนาและสร้างไฟล์เผยแพร่ และใช้ CSS สำหรับรูปแบบหน้าจอ หน้าเว็บแบ่งเป็นหน้าสาธารณะและหน้าพนักงาน ภายในหน้าพนักงานมีเมนูและแบบฟอร์มที่สัมพันธ์กับสิทธิ์ของบัญชี รวมทั้งสถานะกำลังโหลด ไม่มีข้อมูล และข้อผิดพลาด [5]

ไฟล์ package.json เป็นแหล่งข้อมูลชุดเทคโนโลยีที่ใช้จริง รายงานไม่ใช้รายการเทคโนโลยีในแผนเดิมเป็นข้อสรุปหากไม่ตรงกับโค้ดปัจจุบัน และไม่ตีความช่วงเวอร์ชันในไฟล์ดังกล่าวเป็นหลักฐานเวอร์ชันที่ติดตั้งในทุกสภาพแวดล้อม

### 2.3 API และการยืนยันตัวตน

ฝั่งบริการใช้ Express บน Node.js และส่งข้อมูล JSON เส้นทางหลักอยู่ภายใต้ /api โค้ดแยกการตรวจรูปแบบคำขอ การตรวจสิทธิ์ และบริการธุรกิจออกจากกัน ข้อผิดพลาดมีรหัส ข้อความ และ requestId เพื่อช่วยติดตามปัญหา โดยใช้สถานะ HTTP ให้สัมพันธ์กับการตรวจข้อมูล การยืนยันตัวตน สิทธิ์ และความขัดแย้งของรายการ [3], [4]

ระบบปัจจุบันใช้ Bearer session แบบเพิกถอนได้ ผู้ใช้ส่งอีเมลและรหัสผ่าน เมื่อยืนยันสำเร็จบริการสร้างโทเคนสุ่ม บันทึกค่าแฮช SHA-256 ของโทเคนในฐานข้อมูล และกำหนดอายุแปดชั่วโมง รหัสผ่านตรวจด้วย bcryptjs การเรียก API ตรวจว่าเซสชันยังไม่หมดอายุและบัญชียังใช้งานได้ การออกจากระบบลบเซสชัน ฝั่งเว็บเก็บโทเคนในหน่วยความจำของแท็บ เมื่อรีเฟรชจึงต้องเข้าสู่ระบบใหม่ [3], [4], [5]

การซ่อนเมนูในหน้าจอช่วยแสดงงานที่เหมาะกับบทบาท แต่การอนุญาตคำขอเกิดขึ้นที่ฝั่งบริการด้วย ไม่อาศัยการซ่อนเมนูเป็นมาตรการจำกัดสิทธิ์เพียงอย่างเดียว

### 2.4 ฐานข้อมูลและธุรกรรม

โครงการใช้ Prisma เชื่อม MongoDB และกำหนดแบบจำลองใน schema.prisma โดยฐานข้อมูลต้องรองรับธุรกรรมผ่าน replica set ข้อมูลสำคัญประกอบด้วยผู้ใช้ เซสชัน ประเภทห้อง ห้อง ผู้เข้าพัก การจอง สรุปการชำระเงิน รายการรับหรือคืนเงิน และสิทธิ์ห้องรายคืน [1], [7]

การดำเนินงานที่เปลี่ยนหลายชุดข้อมูลใช้ธุรกรรมเพื่อให้ผลการเปลี่ยนแปลงสอดคล้องกัน เช่น การสร้างการจองต้องสัมพันธ์กับสิทธิ์รายคืนและสรุปการชำระเงิน ส่วนการเช็กอินต้องสัมพันธ์กับสถานะการจองและสถานะห้อง โค้ดใช้รุ่นข้อมูลของการจองเพื่อประสานการเขียนพร้อมกันระหว่างงานการเงินกับการเข้าพัก [2], [8]

### 2.5 การป้องกันการจองซ้อนและการส่งรายการเงินซ้ำ

ระบบแทนช่วงเข้าพักด้วยคืนที่รวมวันเช็กอินแต่ไม่รวมวันเช็กเอาต์ เช่น เข้าพักวันที่ 1 และออกวันที่ 3 ใช้คืนวันที่ 1 และ 2 ห้องจึงรองรับการจองถัดไปที่เริ่มวันที่ 3 ได้หากผ่านเงื่อนไขอื่น โมเดล RoomNightClaim มีข้อกำหนดไม่ให้คู่ roomId และ night ซ้ำกัน การตรวจห้องว่างก่อนแสดงผลจึงมีข้อกำหนดฐานข้อมูลรองรับในขั้นตอนบันทึกด้วย [7], [8]

การรับหรือคืนเงินกำหนด Idempotency-Key เพื่อให้การส่งซ้ำด้วยข้อมูลเดิมคืนรายการเดิม โดยไม่เพิ่มรายการเงินซ้ำ หากใช้กุญแจเดิมกับข้อมูลต่างกันจะเกิดข้อผิดพลาด อีกทั้งชนิดรายการ วิธีชำระ และเลขอ้างอิงมีข้อกำหนดไม่ให้ซ้ำ การควบคุมนี้ป้องกันการบันทึกซ้ำในระบบ แต่ไม่ได้ตรวจสอบโดยอัตโนมัติว่าเงินเคลื่อนย้ายจริงในธนาคารแล้ว พนักงานยังต้องตรวจหลักฐาน [2]

## บทที่ 3 การออกแบบและพัฒนาระบบ

### 3.1 การศึกษาข้อกำหนดและขั้นตอนพัฒนา

ใช้ README เอกสารข้อกำหนด API แบบจำลอง Prisma และชุดทดสอบเป็นข้อมูลสำหรับสรุปขอบเขต กระบวนการพัฒนาที่เห็นจากเอกสารแบ่งเป็นข้อมูลพื้นฐานและการเข้าสู่ระบบ บริการการจอง บัญชีรายการเงินและการเข้าพัก แล้วเพิ่ม Dashboard และ Public API ส่วนหน้าเว็บพัฒนาให้ใช้บริการตามข้อกำหนดเหล่านี้ [1], [2], [3], [4], [8]

รายงานไม่กำหนดวันเริ่มพัฒนา ระยะเวลาดำเนินงาน รายชื่อผู้รับผิดชอบรายโมดูล หรือค่าใช้จ่ายขึ้นใหม่ เพราะข้อมูลดังกล่าวยังไม่มีหลักฐานที่ยืนยันครบถ้วนในแหล่งข้อมูลที่ตรวจ

### 3.2 การออกแบบสิทธิ์และกรณีใช้งาน

บุคคลทั่วไปค้นหาห้องว่างและอ่านรายละเอียดห้องผ่าน Public API ได้ ส่วนผู้ใช้ที่เข้าสู่ระบบแบ่งเป็น admin และ receptionist ทั้งสองบทบาทเข้าถึงงานการจองและการดำเนินงานต้อนรับตามข้อกำหนด ผู้ดูแลระบบมีสิทธิ์เพิ่มเติมสำหรับจัดการผู้ใช้ ห้อง ประเภทห้อง และรายงานรวม [3], [4]

กระบวนการจองของพนักงานเริ่มจากค้นหาตามวันและจำนวนคน เลือกห้อง เลือกผู้เข้าพัก ตรวจข้อมูล แล้วส่งคำขอยืนยัน การค้นหาครั้งแรกไม่รับประกันว่าห้องยังว่างเมื่อกดยืนยัน เพราะอาจมีคำขออื่นเข้ามา บริการจึงตรวจเงื่อนไขอีกครั้ง และหน้าจอรองรับกรณีจองชนด้วยการค้นหาใหม่โดยเก็บข้อมูลแบบฟอร์ม [5], [9]

### 3.3 การออกแบบข้อมูล

User เก็บบัญชี บทบาท และสถานะใช้งาน เชื่อมกับ Session และผู้บันทึกรายการ RoomType เก็บชื่อ ความจุ ราคาต่อคืน และสิ่งอำนวยความสะดวก โดยหนึ่งประเภทมีหลาย Room ส่วน Room เก็บหมายเลขห้อง ชั้น และสถานะทางกายภาพ ได้แก่ available, occupied และ maintenance [7]

Guest เก็บข้อมูลผู้เข้าพักและเชื่อมกับ Booking แต่ละ Booking อ้างอิงผู้เข้าพักและห้องหนึ่งรายการ พร้อมวันเข้า วันออก จำนวนคน ราคาต่อคืนที่บันทึกไว้ ยอดรวม สถานะ และผู้สร้างหรือแก้ไข การเก็บราคาในการจองช่วยรักษาราคาของรายการเดิมเมื่อราคาประเภทห้องเปลี่ยน [7], [8]

Booking เชื่อมกับ Payment แบบหนึ่งต่อหนึ่ง Payment เก็บยอดสรุปและสถานะความพร้อมของบัญชีรายการเงิน PaymentTransaction เก็บรายการ receive หรือ refund พร้อมจำนวนเงิน วิธีชำระ เลขอ้างอิง เวลา ผู้บันทึก และกุญแจป้องกันรายการซ้ำ รายการคืนเงินอ้างถึงรายการรับเงินต้นทาง สำหรับ RoomNightClaim แต่ละรายการระบุห้อง การจอง และคืนที่ถูกครอบครอง [2], [7]

โมเดล AdminGuard เป็นข้อมูลควบคุมภายใน และไม่ใช่บทบาทผู้ใช้หรือหน้าจอธุรกิจเพิ่มเติม หมายเลขห้องในฐานข้อมูลยังคงใช้ฟิลด์ number และ collection Room เพื่อรักษาความเข้ากันได้กับข้อมูลเดิม ส่วน API แสดงชื่อ roomNumber ตามข้อกำหนด [7]

### 3.4 การค้นหาห้องว่างและการจอง

คำขอค้นหาใช้ checkInDate, checkOutDate และ guestCount บริการเลือกห้องที่เปิดใช้งาน มีสถานะ available และมีประเภทห้องที่เปิดใช้งานพร้อมความจุเพียงพอ จากนั้นตัดห้องที่มีสิทธิ์ครอบครองในคืนใดคืนหนึ่งของช่วงที่ค้นหาออก ผลลัพธ์ประกอบด้วย roomId, roomNumber, roomType, capacity และ pricePerNight [3]

ข้อจำกัดปัจจุบันคือห้องที่มีสถานะ occupied หรือ maintenance ถูกตัดออกแม้ค้นหาวันในอนาคต จึงต้องอธิบายว่าเป็นกฎของโค้ดปัจจุบัน ไม่กล่าวอ้างว่าเป็นการพยากรณ์ห้องว่างจากกำหนดเช็กเอาต์ทั้งหมด บริการยังโหลดรายการห้องและสิทธิ์ที่เกี่ยวข้องก่อนแบ่งหน้าผลลัพธ์ จึงต้องทดสอบกับจำนวนห้องและช่วงเข้าพักที่เป็นตัวแทนของการใช้งานจริงก่อนเพิ่มปริมาณคำขอ [3]

### 3.5 การบันทึกรับและคืนเงิน

จำนวนเงินใช้จำนวนเต็มหน่วยบาท และมีขอบเขตตาม Prisma Int กำหนดยอดรับสะสมเป็น paidAmount ยอดคืนสะสมเป็น refundedAmount ยอดสุทธิเท่ากับยอดรับลบยอดคืน และยอดคงเหลือเท่ากับยอดเรียกเก็บลบยอดสุทธิ ระบบกำหนดให้ยอดสุทธิไม่ติดลบและไม่เกินยอดเรียกเก็บ [2]

ตัวอย่างเพื่ออธิบายกฎ ไม่ใช่ข้อมูลรายได้จริง: การจองราคา 2,400 บาท รับ 1,000 บาท แล้วคืน 400 บาท จะมียอดสุทธิ 600 บาท การยกเลิกยังทำไม่ได้จนคืนยอดสุทธิที่เหลือทั้งหมด การคืนเงินแต่ละครั้งต้องระบุรายการรับต้นทางและเหตุผล ระบบไม่คืนเงินจริงให้อัตโนมัติเมื่อกดยกเลิก [2]

การรับเงินรองรับสถานะ confirmed และ checked_in ส่วนการคืนเงินรองรับ confirmed การเปลี่ยนยอดจองหรือยกเลิกต้องมียอดสุทธิเป็นศูนย์ ข้อมูลการชำระเงินเดิมที่ยังไม่ตรวจสอบหลักฐานจะถูกปิดกั้นจากการดำเนินงานที่ต้องพึ่งยอดเงิน จนผ่านกระบวนการ reconciliation ตามหลักฐานจริง [2]

### 3.6 การเช็กอิน เช็กเอาต์ และการออกแบบหน้าจอ

การเช็กอินต้องเป็นการจอง confirmed อยู่ในช่วงวันเข้าพักตาม Asia/Bangkok และห้องกับประเภทห้องยังใช้งานได้ โดยห้องต้องพร้อมเข้า ระบบเปลี่ยนสถานะการจองเป็น checked_in และห้องเป็น occupied ในธุรกรรมเดียวกัน การเช็กเอาต์ต้องเป็น checked_in ห้องสัมพันธ์กับการเข้าพักนั้น และชำระครบตามยอดสุทธิ จากนั้นเปลี่ยนสถานะการจองเป็น checked_out และห้องกลับพร้อมใช้งาน [2]

การเช็กเอาต์ก่อนกำหนดยังคงสิทธิ์ครอบครองคืนเดิมไว้ตามข้อกำหนด ไม่คืนคืนที่เหลือให้จองใหม่โดยอัตโนมัติ หากต้องการนโยบายอื่นต้องออกแบบกฎและทดสอบเพิ่มเติม [2]

หน้าสาธารณะใช้ภาพและองค์ประกอบที่จัดเก็บในโครงการ มีแบบฟอร์มค้นหาและการแสดงผลแบบตอบสนองต่อขนาดหน้าจอ หน้าพนักงานมีการเข้าสู่ระบบ Dashboard รายการและรายละเอียดการจอง รวมถึงหน้าตรวจสอบก่อนยืนยัน ใช้กล่องโต้ตอบสำหรับแบบฟอร์มและรายละเอียด พร้อมสถานะโหลด ว่าง และข้อผิดพลาด ข้อมูลรูปแบบหน้าจออ้างจากบันทึกการตรวจ UI ไม่ใช้ภาพโรงแรมในทรัพยากรแทนภาพหน้าจอผลการทำงานจริง [5], [6], [9]

### 3.7 ความปลอดภัยและแนวทางติดตั้ง

บริการจำกัด Public API ที่ 60 คำขอต่อ IP ต่อนาที และการเข้าสู่ระบบที่ 20 คำขอต่อ IP ต่อ 15 นาที มีรายการ origin ที่อนุญาตแยกสำหรับเว็บพนักงานกับเว็บสาธารณะ รวมทั้งขนาดคำขอและส่วนหัว HTTP ที่กำหนดไว้ ตัวนับคำขอเก็บในหน่วยความจำของแต่ละ process จึงยังไม่ใช่ตัวจำกัดร่วมกันระหว่างหลาย instance [3]

เอกสารเสนอการติดตั้งเว็บบน Vercel, API บน Render และฐานข้อมูล MongoDB Atlas พร้อมตัวอย่างไฟล์ตั้งค่า การมีไฟล์เหล่านี้เป็นหลักฐานการเตรียมติดตั้ง แต่ไม่ใช่หลักฐานว่าติดตั้งและเปิดใช้งานจริงสำเร็จแล้ว ฐานข้อมูลเดิมต้องตรวจเป้าหมาย สำรอง ทดลองกู้คืน และตรวจสิทธิ์รายคืนกับรายการเงินก่อนเปิดให้เขียน [1], [10]

## บทที่ 4 ผลการพัฒนาและหลักฐานการทดสอบ

### 4.1 ผลการพัฒนาเชิงฟังก์ชัน

จากซอร์สโค้ดและข้อกำหนดที่ตรวจพบ ระบบมีส่วนแสดงผลสาธารณะและส่วนพนักงาน เส้นทาง API สำหรับการเข้าสู่ระบบ ข้อมูลพื้นฐาน การจอง การบันทึกรายการเงิน การเช็กอินและเช็กเอาต์ Dashboard และรายงานผู้ดูแลระบบ แบบจำลองข้อมูลมีความสัมพันธ์ที่รองรับกระบวนการเหล่านี้ และมีชุดทดสอบอยู่ใน server/tests กับ client/tests [1], [4], [5], [7]

สถานะการพัฒนานี้หมายถึงมีโค้ดและหลักฐานใน repository ไม่ยืนยันว่าทุกความสามารถได้ตรวจรับในสภาพแวดล้อมจริงหรือว่าผู้ใช้โรงแรมได้ใช้งานแล้ว

### 4.2 หลักฐานการทดสอบฝั่งบริการ

บันทึก task5-acceptance.md ลงวันเดียวกันรายงานผล 173 กรณีหลังเพิ่ม Task 5 จำนวน 7 กรณี และรายงานการทดสอบซ้ำหลังปรับ dependencies ผล 166 กับ 173 เป็นคนละรุ่นของชุดทดสอบ จึงไม่รวมเป็น 339 กรณี บันทึก Task 5 ระบุสภาพแวดล้อม Windows, Node 24.21.0, Prisma 6.19.3 และ MongoDB 8.2.6 พร้อมข้อจำกัดด้านการตรวจบนเครื่อง [12]

การทดสอบ rollback เปรียบเทียบข้อมูลที่เกี่ยวข้องก่อนและหลังจำลองความล้มเหลว การทดสอบพร้อมกันตรวจยอดเงิน สิทธิ์ห้อง และสถานะการเข้าพักหลังคำขอแข่งขันกัน หลักฐานนี้สนับสนุนกฎที่ชุดทดสอบครอบคลุม แต่ไม่ใช้แทนการทดสอบการล้มเหลวของระบบฐานข้อมูล production หรือการตรวจการโอนเงินจริง [11]

### 4.3 หลักฐานการทดสอบหน้าจอ

บันทึก bug-ux-fix-acceptance.md ระบุว่าการติดตั้ง ตรวจ lint และ build ฝั่ง client ผ่าน และตรวจลำดับเข้าสู่ระบบ → สร้างการจอง → รับเงิน → เช็กอิน → เช็กเอาต์ → รายงาน → ออกจากระบบกับ MongoDB replica set ชั่วคราวได้ รวมทั้งตรวจเมนูตามบทบาทพนักงานต้อนรับ โดยใช้ข้อมูลจำลอง [9]

บันทึก figma-ui-verification.md ครอบคลุมหน้าจอรุ่นที่ปรับรูปแบบใหม่ ระบุการตรวจ desktop และหน้าจอกว้าง 390 พิกเซล การโหลดภาพ การค้นหา สถานะว่างหรือผิดพลาด และกระบวนการเลือกห้องจนยืนยันการจอง โดยใช้ HTTP fixture ชั่วคราวที่ไม่เรียกฐานข้อมูล [6]

หลักฐานทั้งสองมีขอบเขตต่างกัน การตรวจด้วย fixture สนับสนุนผลด้านการแสดงผลและปฏิสัมพันธ์ แต่ยังไม่ยืนยันการเชื่อมหน้าจอรุ่นใหม่กับ MongoDB จริงทุกเส้นทาง การตรวจครบกระบวนการอีกครั้งใน staging จึงยังจำเป็น

### 4.4 Dashboard รายงาน และ Public API

Dashboard แสดงจำนวนห้องว่างสำหรับคืนนี้ ห้องที่มีสถานะ occupied และกำหนดการเข้าออกในวันโรงแรม จำนวนห้องว่างกับห้อง occupied ไม่จำเป็นต้องรวมกันเท่าจำนวนห้องทั้งหมด เพราะมีห้องที่ปิดใช้งานหรือซ่อมบำรุง การนับแต่ละส่วนเป็นการอ่านข้อมูลสดแยกกัน ไม่ใช่ภาพฐานข้อมูลชุดเดียวขณะมีการเขียนพร้อมกัน [3]

รายงานแสดง receivedBaht, refundedBaht, netBaht และจำนวน Payment ที่ยังไม่ reconcile โดยอ้างรายการเงินสะสมทั้งหมด จึงไม่ตีความ netBaht เป็นกำไรหรือรายได้ทางบัญชีที่รับรู้ตามช่วงเวลา Public API คืนข้อมูลห้องห้าฟิลด์ตามที่กำหนด และไม่คืนรายละเอียดผู้เข้าพักหรือข้อมูลการชำระเงิน [3]

### 4.5 ข้อจำกัดของผลประเมิน

ผลผ่านและผลตรวจ dependency audit ในเอกสารเป็นผล ณ วันที่บันทึก ไม่ใช่สถานะการทดสอบหรือความปลอดภัยล่าสุดที่ยืนยันใหม่ในวันที่เขียนรายงาน ไม่มีหลักฐาน remote CI ที่ผ่านล่าสุด การทบทวนจากผู้ประเมิน การเปิดใช้จริง หรือการทดสอบกู้คืนข้อมูล production ในแหล่งข้อมูลที่ตรวจ [9], [12]

ยังไม่มีการทดลองประสิทธิภาพด้วยจำนวนห้องและผู้ใช้จริง การประเมินความพึงพอใจ หรือข้อมูลสถิติเปรียบเทียบก่อนและหลัง จึงไม่ระบุค่าความเร็ว ความถูกต้องร้อยละ 100 หรือระดับความพึงพอใจขึ้นเอง ผลในบทนี้เป็นการสรุปหลักฐานการพัฒนาและการทดสอบที่มีอยู่เท่านั้น

## บทที่ 5 สรุปและข้อเสนอแนะ

### 5.1 สรุปผลโครงการ

Hotel-Lobby มีโครงสร้างเว็บและ API ที่รองรับงานข้อมูลพื้นฐาน การจอง รายการเงิน และการเข้าพัก โดยใช้ React/TypeScript กับ Express และ Prisma/MongoDB ส่วนสำคัญคือการป้องกันสิทธิ์ห้องรายคืนซ้ำ การประสานงานเขียนด้วยธุรกรรม และการผูกยอดเงินกับรายการรับหรือคืนเงิน เว็บไซต์สาธารณะใช้บริการค้นหาห้องว่างร่วมกับระบบพนักงาน [1], [2], [3], [7]

หลักฐานในโครงการแสดงว่ามีการทดสอบบริการและการตรวจหน้าจอในสภาพแวดล้อมทดลอง แต่การนำไปใช้งานจริงยังต้องตรวจการเชื่อมระบบรุ่นปัจจุบัน การติดตั้ง ข้อมูลเดิม ประสิทธิภาพ และแนวทางปฏิบัติของพนักงาน รายงานจึงสรุปผลตามหลักฐานโดยไม่รับรองความพร้อม production เกินกว่าข้อมูลที่มี

### 5.2 ข้อเสนอแนะก่อนนำไปใช้จริง

ควรตั้ง staging ให้มีโครงสร้างใกล้การใช้งานจริงและทดสอบครบกระบวนการด้วยข้อมูลจำลอง ตรวจ origin ของเว็บและ API ตรวจการหมดอายุหรือเพิกถอนเซสชัน และตรวจการทำงานบนมือถือกับแป้นพิมพ์ รวมถึงกรณีเครือข่ายขาดระหว่างบันทึกรายการเงินหรือเปลี่ยนสถานะ

ควรตรวจฐานข้อมูลเดิมบนสำเนา ทดลองสำรองและกู้คืน ตรวจข้อกำหนดไม่ให้สิทธิ์ห้องซ้ำ และ reconcile รายการเงินจากหลักฐานที่ตรวจสอบได้ กำหนดความรับผิดชอบของพนักงานในการตรวจใบรับเงิน การคืนเงิน และเลขอ้างอิง เพื่อให้ความถูกต้องของข้อมูลในระบบสัมพันธ์กับการปฏิบัติงานจริง [2], [10]

ควรทดสอบประสิทธิภาพด้วยจำนวนห้อง ช่วงเข้าพัก และปริมาณคำขอที่ใกล้การใช้งานเป้าหมาย หากใช้ API หลาย instance ต้องมีตัวจำกัดคำขอร่วมกันหรือที่ขอบระบบ พร้อมกำหนดนโยบายข้อมูลผู้เข้าพัก สิทธิ์เข้าถึง และระยะเวลาเก็บตามบริบทของหน่วยงาน

### 5.3 แนวทางพัฒนาต่อ

แนวทางเพิ่มเติมได้แก่การรองรับการค้นหาห้อง occupied สำหรับวันในอนาคตตามกำหนดการออก การกำหนดช่วงซ่อมบำรุง การปรับการแบ่งหน้าที่ระดับฐานข้อมูล และรายงานรายการเงินตามช่วงเวลา แต่ละส่วนต้องมีข้อกำหนดและกรณีทดสอบใหม่เพื่อไม่ให้ขัดกับกฎการจองและข้อมูลเดิม

หากเพิ่มการจองและชำระเงินออนไลน์ ต้องออกแบบการยืนยันผู้จอง การหมดอายุการถือห้อง การตรวจผลชำระเงิน และการคืนเงินที่สอดคล้องกับผู้ให้บริการจริง ความสามารถเหล่านี้เป็นข้อเสนอแนะในอนาคต ไม่ใช่ฟังก์ชันที่ระบบปัจจุบันมีแล้ว
