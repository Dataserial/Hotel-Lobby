# ข้อมูลที่ต้องเติมและตรวจสอบสำหรับรายงาน v1

รายงาน `hotel_management_academic_report_v1.docx` และ `.pdf` จัดตามตัวอย่าง **รายงานวิชาการ 3 บท** ฉบับใหม่ โดยมีบทคัดย่อ คำนำ สารบัญ สารบัญภาพ เอกสารอ้างอิง และใบรับรองโครงงาน เนื้อหาระบบโรงแรมอ้างจากแผนพัฒนาที่แนบมา ซึ่งเป็นแผนและข้อกำหนดเบื้องต้น ยังไม่ใช่หลักฐานว่าระบบสร้างหรือทดสอบเสร็จแล้ว

## ข้อมูลหน้าปก คำนำ และใบรับรอง

- [ ] กรอกชื่อและรหัสนักศึกษาของสมาชิก 5 คน ตรวจสะกดชื่อภาษาไทย/อังกฤษ
- [ ] กรอกชื่อและตำแหน่งอาจารย์ที่ปรึกษา
- [ ] กรอกรหัส/ชื่อวิชา ภาคเรียน ปีการศึกษา สาขาวิชา คณะ/วิทยาลัย มหาวิทยาลัย และเดือน/ปีของรายงาน
- [ ] กรอกชื่อผู้จัดทำและวันที่ท้ายคำนำ รวมถึงชื่อ วันที่ และลายเซ็นในใบรับรอง
- [ ] ยืนยันชื่อโครงงานภาษาไทยและภาษาอังกฤษอย่างเป็นทางการ
- [ ] หากสถาบันกำหนดตราสัญลักษณ์หรือรูปแบบหน้าปกเฉพาะ ให้แนบไฟล์ตรา/คู่มือรูปแบบก่อนแก้ไข

## ข้อมูลที่ต้องยืนยันก่อนพัฒนาหรือปรับบทที่ 2 และ 3

- [ ] **กำหนดเวลา:** แผนต้นทางใช้หัวข้อ “1 สัปดาห์” กับรายการ 17 ขั้นตอน แต่หัวข้อความเสี่ยงกล่าวถึง “6 สัปดาห์” ต้องกำหนดวันเริ่ม วันส่ง และระยะจริงของแต่ละขั้น
- [ ] **เทคโนโลยีฐานข้อมูล:** ต้นทางระบุ MongoDB Atlas + Mongoose พร้อมกับ Prisma ORM ในอีกจุด ต้องเลือกชุดที่ใช้จริงและปรับส่วน 2.3.2
- [ ] **การเข้าสู่ระบบ:** เลือก JWT ใน HttpOnly cookie หรือ Express Session แล้วกำหนดอายุเซสชัน การออกจากระบบ และการป้องกันคำขอข้ามไซต์ให้ตรงกับแบบที่เลือก
- [ ] **สิทธิ์ Rooms:** ยืนยันว่า Receptionist อ่าน/ค้นหาเท่านั้น หรือแก้ไขห้องพักได้บางกรณี เพราะตารางสิทธิ์และ API ในต้นทางยังไม่ชัด
- [ ] **Public Availability API:** ยืนยันว่าเปิดสาธารณะหรือใช้ API key, เส้นทาง API ฉบับสุดท้าย, rate limit และ CORS
- [ ] **กฎห้องว่าง:** ระบุวิธีใช้สถานะ `occupied` กับการค้นหาวันในอนาคต และวิธีจัดการห้อง `maintenance` ที่มีช่วงเวลาเริ่ม/สิ้นสุด
- [ ] **กฎการจอง:** ยืนยันช่วงวันเข้าพัก การเปลี่ยนห้อง การยกเลิกหลังชำระเงิน และวิธีป้องกันจองซ้อนจากคำขอพร้อมกันที่ฐานข้อมูล/บริการ
- [ ] **การชำระเงิน:** กำหนดเงื่อนไขยอดค้าง จ่ายบางส่วน คืนเงินภายนอก และการเช็กเอาต์ให้ชัด เพราะ MVP บันทึกสถานะเท่านั้น ไม่เชื่อม Payment Gateway
- [ ] **ข้อมูลส่วนบุคคล:** กำหนดข้อมูลเอกสารที่จำเป็น ผู้มีสิทธิ์เข้าถึง วิธีปกปิด ระยะเวลาเก็บ และข้อมูลจำลองสำหรับทดสอบ
- [ ] **รายงานบน Dashboard:** ระบุรายการตัวชี้วัดและช่วงเวลาของรายงาน Admin ที่ต้องการจริง
- [ ] ระบุโรงแรมกรณีศึกษา/สถานที่พัฒนา หากไม่มีให้ยืนยันว่าใช้ข้อมูลจำลองทั้งหมด

## หลักฐานที่ต้องมีหากจะเขียนรายงานผลการพัฒนาจริง

- [ ] Repository, README, Data Model/ER, เอกสาร API, ภาพหน้าจอ และคู่มือใช้งานระบบจริง
- [ ] รายชื่อเจ้าของงานและผู้ทบทวนทั้ง 5 คน พร้อมสถานะงานที่ตรวจรับแล้ว รายการ Step ในแผนยังใช้แทนหลักฐานเสร็จไม่ได้
- [ ] ผล Unit/Integration/System Test สำหรับ Auth, สิทธิ์, CRUD, ค้นหา, กฎวันที่, การจองพร้อมกัน, เช็กอิน/เช็กเอาต์ และสถานะชำระเงิน
- [ ] Postman Collection หรือผลเรียก Public API จากไคลเอนต์ภายนอก รวมกรณีข้อมูลผิดและตรวจว่าไม่คืนข้อมูลผู้เข้าพัก
- [ ] บันทึกบั๊ก ผลทดสอบหลังแก้ Security Checklist และการตรวจ responsive/loading/error/empty state
- [ ] URL Demo และหลักฐาน deploy จริง หากยังไม่มีให้คงถ้อยคำว่า “แผนการนำไปใช้”
- [ ] หากต้องการกล่าวถึงความเร็ว ความถูกต้อง หรือความพึงพอใจ ให้กำหนดกลุ่มตัวอย่าง วิธีวัด จำนวนรอบ และผลจริงก่อนสรุป
