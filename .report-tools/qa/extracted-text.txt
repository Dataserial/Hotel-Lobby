1.1 ความเป็นมาและความสำคัญ 
งานต้อนรับของโรงแรมต้องประสานข้อมูลหลายส่วน ได้แก่ ห้องพัก ผู้ เข้าพัก ช่วงวันจอง สถานะ
การเข้าพัก และ รายการชำระเงิน หาก ข้อมูลเหล่านี้แยกจากกัน พนักงาน ต้องตรวจสอบหลายแหล่งก่อน
ยืนยันรายการ และ อาจเกิดความไม่สอดคล้องระหว่างห้องที่แสดงว่าว่างกับห้องที่ได้รับการจองแล้ว 
โครงการนี้จึงกำหนดให้ข้อมูลการจองและการดำเนินงานเชื่อมโยงกันผ่านบริการกลาง 
ประเด็นสำคัญของระบบคือการป้องกันการจองห้องเดียวกันในคืนเดียวกันเมื่อมีคำขอพร้อมกัน 
และการป้องกันยอดเงินที่ไม่สัมพันธ์กับหลักฐานรับหรือคืนเงิน โค้ด ใช้ข้อมูลสิทธิ์ครอบครองห้องรายคืน
และธุรกรรมฐานข้อมูลเพื่อควบคุมการจอง พร้อม เก็บรายการเงินที่เชื่อมโยงกับการจองเพื่อให้ตรวจสอบ
ย้อนหลังได้ ส่วนเว็บไซต์สาธารณะแสดงเฉพาะข้อมูลห้องว่างตามขอบเขตที่กำหนด [1], [2], [3] 
ไม่มีหลักฐานการสำรวจโรงแรมหรือข้อมูลสัมภาษณ์ผู้ใช้งานจริงในชุดเอกสารที่ใช้เขียนรายงาน 
จึงอธิบายปัญหาเป็นบริบทการออกแบบระบบ ไม่ สรุปว่าปัญหาดังกล่าวเกิดขึ้นจริงในโรงแรมกรณีศึกษา
แห่งใด

1.3 ขอบเขตของระบบ

1.4 ประโยชน์ที่คาดว่าจะได้รับ

เดียวกัน มีเงื่อนไขตรวจสอบก่อนเปลี่ยนสถานะ และมีรายการอ้างอิงสำหรับตรวจสอบธุรกรรม ข้อมูลห้อง

2.1 เว็บแอปพลิเคชันและสถาปัตยกรรมระบบ 
โครงการแยกส่วนแสดงผลไว้ในโฟลเดอร์ client และส่วนให้บริการข้อมูลไว้ในโฟลเดอร์ server 
ฝั่งผู้ใช้ส่งคำขอ HTTP ไปยัง API ซึ่งตรวจข้อมูลและสิทธิ์ก่อนเรียกบริการและฐานข้อมูล การ แยกส่วน
ทำให้หน้าจอสามารถใช้กฎธุรกิจเดียวกันผ่าน API และทำให้การทดสอบบริการไม่จำเป็นต้องอาศัยการกด
หน้าจอทุกกรณี [1], [4], [5] 
เส้นทางการทำงานหลักคือผู้ใช้ → React/TypeScript → Express API → บริการการจอง
หรือรายการเงิน → Prisma → MongoDB รูปแบบนี้เป็นคำอธิบายจากโครงสร้างโค้ดปัจจุบัน ไม่ ใช่
หลักฐานว่าระบบถูกติดตั้งตามสถาปัตยกรรมนี้บนบริการโฮสต์จริงแล้ว 
2.2 เทคโนโลยีส่วนแสดงผล 
ส่วนแสดงผลใช้ React และ TypeScript โดยมี Vite สำหรับพัฒนาและสร้างไฟล์เผยแพร่ และ
ใช้ CSS สำหรับรูปแบบหน้าจอ หน้า เว็บแบ่งเป็นหน้าสาธารณะและหน้าพนักงาน ภายใน หน้าพนักงานมี
เมนูและแบบฟอร์มที่สัมพันธ์กับสิทธิ์ของบัญชี รวมทั้งสถานะกำลังโหลด ไม่มีข้อมูล และข้อผิดพลาด [5] 
ไฟล์ package.json เป็นแหล่งข้อมูลชุดเทคโนโลยีที่ใช้จริง รายงาน ไม่ใช้รายการเทคโนโลยีใน
แผนเดิมเป็นข้อสรุปหากไม่ตรงกับโค้ดปัจจุบัน และ ไม่ตีความช่วงเวอร์ชันในไฟล์ดังกล่าวเป็นหลักฐาน
เวอร์ชันที่ติดตั้งในทุกสภาพแวดล้อม 
2.3 API และการยืนยันตัวตน 
ฝั่งบริการใช้ Express บน Node.js และส่งข้อมูล JSON เส้นทางหลักอยู่ภายใต้ / api โค้ดแยก
การตรวจรูปแบบคำขอ การ ตรวจสิทธิ์ และ บริการธุรกิจออกจากกัน ข้อผิดพลาด มีรหัส ข้อความ และ 
requestId เพื่อช่วยติดตามปัญหา โดย ใช้สถานะ HTTP ให้สัมพันธ์กับการตรวจข้อมูล การ ยืนยันตัวตน 
สิทธิ์ และความขัดแย้งของรายการ [3], [4] 
ระบบปัจจุบันใช้ Bearer session แบบเพิกถอนได้ ผู้ใช้ ส่งอีเมลและรหัสผ่าน เมื่อ ยืนยันสำเร็จ
บริการสร้างโทเคนสุ่ม บันทึก ค่าแฮช SHA-256 ของโทเคนในฐานข้อมูล และ กำหนดอายุแปดชั่วโมง 
รหัสผ่านตรวจด้วย bcryptjs การเรียก API ตรวจว่าเซสชันยังไม่หมดอายุและบัญชียังใช้งานได้ การ
ออกจากระบบลบเซสชัน ฝั่ง เว็บเก็บโทเคนในหน่วยความจำของแท็บ เมื่อ รีเฟรชจึงต้องเข้าสู่ระบบใหม่ 
[3], [4], [5] 
การซ่อนเมนูในหน้าจอช่วยแสดงงานที่เหมาะกับบทบาท แต่ การอนุญาตคำขอเกิดขึ้นที่ฝั่งบริการ
ด้วย ไม่อาศัยการซ่อนเมนูเป็นมาตรการจำกัดสิทธิ์เพียงอย่างเดียว

2.4 ฐานข้อมูลและธุรกรรม 
โครงการใช้ Prisma เชื่อม MongoDB และกำหนดแบบจำลองใน schema.prisma โดย
ฐานข้อมูลต้องรองรับธุรกรรมผ่าน replica set ข้อมูลสำคัญประกอบด้วยผู้ใช้ เซสชัน ประเภทห้อง ห้อง 
ผู้เข้าพัก การจอง สรุปการชำระเงิน รายการรับหรือคืนเงิน และสิทธิ์ห้องรายคืน [1], [7] 
การดำเนินงานที่เปลี่ยนหลายชุดข้อมูลใช้ธุรกรรมเพื่อให้ผลการเปลี่ยนแปลงสอดคล้องกัน เช่น 
การสร้างการจองต้องสัมพันธ์กับสิทธิ์รายคืนและสรุปการชำระเงิน ส่วน การเช็กอินต้องสัมพันธ์กับสถานะ
การจองและสถานะห้อง โค้ด ใช้รุ่นข้อมูลของการจองเพื่อประสานการเขียนพร้อมกันระหว่างงานการเงิน

2.5 การป้องกันการจองซ้อนและการส่งรายการเงินซ้ำ 
ระบบแทนช่วงเข้าพักด้วยคืนที่รวมวันเช็กอินแต่ไม่รวมวันเช็กเอาต์ เช่น เข้า พักวันที่ 1 และ ออก
วันที่ 3 ใช้คืน วันที่ 1 และ 2 ห้อง จึงรองรับการจองถัดไปที่เริ่มวันที่ 3 ได้ หากผ่านเงื่อนไขอื่น โมเดล 
RoomNightClaim มีข้อกำหนดไม่ให้คู่ roomId และ night ซ้ำกัน การ ตรวจห้องว่างก่อนแสดงผลจึงมี
ข้อกำหนดฐานข้อมูลรองรับในขั้นตอนบันทึกด้วย [7], [8] 
การรับหรือคืนเงินกำหนด Idempotency-Key เพื่อให้การส่งซ้ำด้วยข้อมูลเดิมคืนรายการเดิม 
โดยไม่เพิ่มรายการเงินซ้ำ หาก ใช้กุญแจเดิมกับข้อมูลต่างกันจะเกิดข้อผิดพลาด อี กทั้งชนิดรายการ วิธี
ชำระ และ เลขอ้างอิงมีข้อกำหนดไม่ให้ซ้ำ การควบคุม นี้ป้องกันการบันทึกซ้ำในระบบ แต่ ไม่ได้ตรวจสอบ
โดยอัตโนมัติว่าเงินเคลื่อนย้ายจริงในธนาคารแล้ว พนักงานยังต้องตรวจหลักฐาน [2]

ขอบเขต กระบวน การพัฒนาที่เห็นจากเอกสารแบ่งเป็นข้อมูลพื้นฐานและการเข้าสู่ระบบ บริการ การจอง 
บัญชีรายการเงินและการเข้าพัก แล้วเพิ่ม Dashboard และ Public API ส่วนหน้าเว็บพัฒนาให้ใช้บริการ
ตามข้อกำหนดเหล่านี้ [1], [2], [3], [4], [8] 
รายงานไม่กำหนดวันเริ่มพัฒนา ระยะเวลา ดำเนินงาน รายชื่อ ผู้รับผิดชอบรายโมดูล หรือ
ค่าใช้จ่ายขึ้นใหม่ เพราะข้อมูลดังกล่าวยังไม่มีหลักฐานที่ยืนยันครบถ้วนในแหล่งข้อมูลที่ตรวจ 
3.2 การออกแบบสิทธิ์และกรณีใช้งาน 
บุคคลทั่วไปค้นหาห้องว่างและอ่านรายละเอียดห้องผ่าน Public API ได้ ส่วน ผู้ใช้ที่เข้าสู่ระบบ
แบ่งเป็น admin และ receptionist ทั้งสองบทบาทเข้าถึงงานการจองและการดำเนินงานต้อนรับตาม
ข้อกำหนด ผู้ดูแลระบบมีสิทธิ์เพิ่มเติมสำหรับจัดการผู้ใช้ ห้อง ประเภทห้อง และรายงานรวม [3], [4] 
กระบวนการจองของพนักงานเริ่มจากค้นหาตามวันและจำนวนคน เลือก ห้อง เลือก ผู้เข้าพัก 
ตรวจข้อมูล แล้ว ส่งคำขอยืนยัน การ ค้นหาครั้งแรกไม่รับประกันว่าห้องยังว่างเมื่อกดยืนยัน เพราะ อาจมี
คำขออื่นเข้ามา บริการ จึงตรวจเงื่อนไขอีกครั้ง และ หน้าจอรองรับกรณีจองชนด้วยการค้นหาใหม่โดยเก็บ
ข้อมูลแบบฟอร์ม [5], [9] 
3.3 การออกแบบข้อมูล 
User เก็บบัญชี บทบาท และสถานะใช้งาน เชื่อมกับ Session และผู้บันทึกรายการ RoomType 
เก็บชื่อ ความจุ ราคา ต่อคืน และ สิ่งอำนวยความสะดวก โดย หนึ่งประเภทมีหลาย Room ส่วน Room 
เก็บหมายเลขห้อง ชั้น และสถานะทางกายภาพ ได้แก่ available, occupied และ maintenance [7] 
Guest เก็บข้อมูลผู้เข้าพักและเชื่อมกับ Booking แต่ละ Booking อ้างอิงผู้เข้าพักและห้องหนึ่ง
รายการ พร้อม วันเข้า วัน ออก จำนวน คน ราคาต่อคืนที่บันทึกไว้ ยอดรวม สถานะ และ ผู้สร้างหรือแก้ไข 
การเก็บราคาในการจองช่วยรักษาราคาของรายการเดิมเมื่อราคาประเภทห้องเปลี่ยน [7], [8] 
Booking เชื่อมกับ Payment แบบหนึ่งต่อหนึ่ง Payment เก็บยอดสรุปและสถานะความพร้อม
ของบัญชีรายการเงิน PaymentTransaction เก็บรายการ receive หรือ refund พร้อมจำนวนเงิน วิธี
ชำระ เลขอ้างอิง เวลา ผู้บันทึก และ กุญแจป้องกันรายการซ้ำ รายการคืนเงินอ้างถึงรายการรับเงินต้นทาง 
สำหรับ RoomNightClaim แต่ละรายการระบุห้อง การจอง และคืนที่ถูกครอบครอง [2], [7]

จำนวนห้องและช่วงเข้าพักที่เป็นตัวแทนของการใช้งานจริงก่อนเพิ่มปริมาณคำขอ [3] 
3.5 การบันทึกรับและคืนเงิน 
จำนวนเงินใช้จำนวนเต็มหน่วยบาท และ มีขอบเขตตาม Prisma Int กำหนดยอดรับสะสมเป็น 
paidAmount ยอดคืนสะสมเป็น refundedAmount ยอดสุทธิเท่ากับยอดรับลบยอดคืน และ ยอด
คงเหลือเท่ากับยอดเรียกเก็บลบยอดสุทธิ ระบบกำหนดให้ยอดสุทธิไม่ติดลบและไม่เกินยอดเรียกเก็บ [2] 
ตัวอย่างเพื่ออธิบายกฎ ไม่ใช่ข้อมูลรายได้จริง: การจองราคา 2,400 บาท รับ 1,000 บาท แล้วคืน 
400 บาท จะ มียอดสุทธิ 600 บาท การ ยกเลิกยังทำไม่ได้จนคืนยอดสุทธิที่เหลือทั้งหมด การ คืนเงิน
แต่ละครั้งต้องระบุรายการรับต้นทางและเหตุผล ระบบไม่คืนเงินจริงให้อัตโนมัติเมื่อกดยกเลิก [2] 
การรับเงินรองรับสถานะ confirmed และ checked_in ส่วนการคืนเงินรองรับ confirmed 
การเปลี่ยนยอดจองหรือยกเลิกต้องมียอดสุทธิเป็นศูนย์ ข้อมูล การชำระเงินเดิมที่ยังไม่ตรวจสอบหลักฐาน
จะถูกปิดกั้นจากการดำเนินงานที่ต้องพึ่งยอดเงิน จน ผ่านกระบวนการ reconciliation ตามหลักฐานจริง 
[2]

ผลผ่านและผลตรวจ dependency audit ในเอกสารเป็นผล ณ วันที่ บันทึก ไม่ ใช่สถานะการ
ทดสอบหรือความปลอดภัยล่าสุดที่ยืนยันใหม่ในวันที่เขียนรายงาน ไม่มีหลักฐาน remote CI ที่ผ่านล่าสุด 
การทบทวนจากผู้ประเมิน การเปิดใช้จริง หรือการทดสอบกู้คืนข้อมูล production ในแหล่งข้อมูลที่ตรวจ 
[9], [12] 
ยังไม่มีการทดลองประสิทธิภาพด้วยจำนวนห้องและผู้ใช้จริง การประเมิน ความพึงพอใจ หรือ
ข้อมูลสถิติเปรียบเทียบก่อนและหลัง จึง ไม่ระบุค่าความเร็ว ความถูกต้ องร้อยละ 100 หรือ ระดับ
ความพึงพอใจขึ้นเอง ผลในบทนี้เป็นการสรุปหลักฐานการพัฒนาและการทดสอบที่มีอยู่เท่านั้น

5.1 สรุปผลโครงการ 
Hotel-Lobby มีโครงสร้างเว็บและ API ที่รองรับงานข้อมูลพื้นฐาน การ จอง ราย การเงิน และ
การเข้าพัก โดยใช้ React/TypeScript กับ Express และ Prisma/MongoDB ส่วนสำคัญคือการป้องกัน
สิทธิ์ห้องรายคืนซ้ำ การประสานงาน เขียนด้วยธุรกรรม และ การผูกยอดเงินกับรายการรับหรือคืนเงิน 
เว็บไซต์สาธารณะใช้บริการค้นหาห้องว่างร่วมกับระบบพนักงาน [1], [2], [3], [7] 
หลักฐานในโครงการแสดงว่ามีการทดสอบบริการและการตรวจหน้าจอในสภาพแวดล้อมทดลอง 
แต่การนำไปใช้งานจริงยังต้องตรวจการเชื่อมระบบรุ่นปัจจุบัน การ ติดตั้ง ข้อมูล เดิม ประสิทธิภาพ และ
แนวทางปฏิบัติของพนักงาน รายงาน จึงสรุปผลตามหลักฐานโดยไม่รับรองความพร้อม production เกิน
กว่าข้อมูลที่มี 
5.2 ข้อเสนอแนะก่อนนำไปใช้จริง 
ควรตั้ง staging ให้มีโครงสร้างใกล้การใช้งานจริงและทดสอบครบกระบวนการด้วยข้อมูลจำลอง 
ตรวจ origin ของเว็บและ API ตรวจการหมดอายุหรือเพิกถอนเซสชัน และ ตรวจการทำงานบนมือถือกับ
แป้นพิมพ์ รวมถึงกรณีเครือข่ายขาดระหว่างบันทึกรายการเงินหรือเปลี่ยนสถานะ 
ควรตรวจฐานข้อมูลเดิมบนสำเนา ทดลองสำรองและกู้คืน ตรวจข้อกำหนดไม่ให้สิทธิ์ห้องซ้ำ และ 
reconcile รายการเงินจากหลักฐานที่ตรวจสอบได้ กำหนด ความรับผิดชอบของพนักงานในการตรวจใบ
รับเงิน การ คืนเงิน และ เลขอ้างอิง เพื่อให้ ความถูกต้องของข้อมูลในระบบสัมพันธ์กับการปฏิบัติงานจริง 
[2], [10] 
ควรทดสอบประสิทธิภาพด้วยจำนวนห้อง ช่วง เข้าพัก และ ปริมาณคำขอที่ใกล้การใช้งาน
เป้าหมาย หาก ใช้ API หลาย instance ต้องมีตัวจำกัดคำขอร่วมกันหรือที่ขอบระบบ พร้อม กำหนด
นโยบายข้อมูลผู้เข้าพัก สิทธิ์เข้าถึง และระยะเวลาเก็บตามบริบทของหน่วยงาน 
5.3 แนวทางพัฒนาต่อ 
แนวทางเพิ่มเติมได้แก่การรองรับการค้นหาห้อง occupied สำหรับวันในอนาคตตามกำหนดการ
ออก การ กำหนดช่วงซ่อมบำรุง การ ปรับการแบ่งหน้าที่ระดับฐานข้อมูล และ รายงานรายการเงินตาม
ช่วงเวลา แต่ละส่วนต้องมีข้อกำหนดและกรณีทดสอบใหม่เพื่อไม่ให้ขัดกับกฎการจองและข้อมูลเดิม 
หากเพิ่มการจองและชำระเงินออนไลน์ ต้อง ออกแบบการยืนยันผู้จอง การ หมดอายุการถือห้อง 
การตรวจผลชำระเงิน และ การคืนเงินที่สอดคล้องกับผู้ให้บริการจริง ความสามารถ เหล่านี้เป็น
ข้อเสนอแนะในอนาคต ไม่ใช่ฟังก์ชันที่ระบบปัจจุบันมีแล้ว
